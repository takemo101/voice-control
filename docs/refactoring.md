# リファクタリングの観点

既存のコードを見直して、**動作を変えずに**、読みやすく・変えやすくするときの観点と進め方。「リファクタリングを見て」と頼むときの土台にする。製品要件は変えない（正本は [SPEC](../SPEC.md)）。原則は [参考にした設計原則](references.md)、書き方は [コーディング指針](coding-guidelines.md)、Module の責務は [構成説明](architecture.md)。

観点の発想は、meeting-analyzer の同名の文書（[desloppify](https://github.com/peteromallet/desloppify) の主観レビューの観点を借りたもの）に倣い、このリポジトリの規則に合わせて書いた。ツールは導入していない。

## 進め方

1. **範囲を決める**：1 つの Module、または 1 つの責務。全体を一度に見ない（量が増えると、指摘が浅くなる）。
2. **観察**：下の観点ごとに、コードを**直接読んで**、根拠（ファイルと行）を集める。警告・テスト結果・`grep` の件数は、**見る場所の目印**で、根拠ではない。
3. **判断**：観点ごとに、「読む人・変える人を助けているか」を言葉で判断する。件数や点数を、目標にしない。
4. **優先**：影響（変更が波及する範囲・誤りの起きやすさ）が大きく、直しやすいものから。構造の指摘（責務・依存の向き）と、局所の指摘（名前・分岐）の両方を扱う。
5. **直す**：小さな変更ごとに。**動作を変えない**。直す前に、守る振る舞いを確かめるテストがあるか見る（なければ、先に足す。配線・文言を固定するテストは足さない）。直したら、`just test`（フィルタなしで全ターゲット）と、CI の結果（CI は、全ターゲットのテストを 1 つのプロセスで並行に動かす。ローカルの `just test` は、ターゲットごとの別の実行）。プロンプト（選択肢の説明・「操作の依頼か」の判定）に触れたなら、`just eval` で、当たり率が変わっていないことを確かめる。利用者に見える出力に触れたなら、変更の前後の `vc` を、`NO_COLOR=1`・一時の `VC_HOME` で動かして、出力を比べる。**機能の追加・仕様の変更を混ぜない**。

## 観点

| 観点 | 見るもの | 見ないもの |
|---|---|---|
| **責務と依存の向き** | 依存が下向きだけか（`vc` → `VCSkill`・`VCSpeech`〔互いには依存しない〕、`VCSkill` → `VCDecision`、`VCCore` は全ターゲットが使う。`Package.swift` が宣言し、コンパイラが強制する）。状態の所有者が 1 か所か（構成説明の表と一致するか）。`vc`（`Commands/`・`CommandContext`）に、規則・判断が入り込んでいないか | 意図した窓口。置き場所の好みだけの違い |
| **抽象の見合い** | 中継するだけで、検査・変換を足さない型や関数。実装が 1 つで、差し替えの必要がない protocol。呼び出し側が、本来の入口を迂回していないか | テストのための差し替え口（`OptionScorer`） |
| **失敗の扱いの一貫性** | `throws`・`Result`・`nil` の混在。境界で原因を失って包み直されていないか。握りつぶし（`try?`）。失敗が、成功に見える代用品になっていないか。見せ方を、境界以外が決めていないか | 意図した、最上位の受け口 |
| **信頼の境界** | 外から来た値（発話・画面・言語モデルの出力・ファイル）が、検査なしに、実行・保存・表示されていないか。許可の判断が、プロンプトに任されていないか。シェルを経由する経路がないか | |
| **並行と所有** | 共有する可変状態が、ロック・`@MainActor`・1 つのスレッドのどれかで守られているか。`@unchecked Sendable` の型に、理由のコメントがあり、内部が**すべて**ロックの下か。主スレッド専用の型が、`@unchecked Sendable` で隠されていないか。`NSApplication.run()` の前に `await` がないか。待つ側が、読む側と同じ共有のスレッド（GCD の共有）を塞いでいないか | 実機でしか起きない競合を、単体テストで再現できないこと（そのときは、理由と、確かめた方法を残す） |
| **名前と契約** | 名前と振る舞いの不一致。何もしないことを隠す名前（`process`・`handle`・`manage`）。型・戻り値・コメントが、動作と食い違っていないか。同じ概念に複数の語がないか。似た別の概念の取り違えを招く名前がないか | 慣習として一貫した短い名前 |
| **論理の明快さ** | 到達しない分岐・両側が同じ分岐・常に真（偽）の条件。深い入れ子（早期の `return` で平らにできるか）。1 つの関数が複数の理由で長くなっていないか | 単一の責務で長い関数。**細かく割ること自体を目的にしない** |
| **古い経路の残り** | 切り替えの後に残った旧い経路・別名・互換の層。使われない設定・型・文言。新旧が同居している API | 外部の利用者がいる互換（理由が書いてあるもの） |
| **プロンプトと選択肢** | 選択肢の説明が、互いに衝突していないか（「取り消し」が、キーにも要素にもある、など）。門番の正規表現が、コーパスの文に合わせただけでないか。説明文の変更が、測定の裏づけを持つか | 測定で効果を確かめた文面 |
| **コメントと文書** | 実態とずれたコメント・文書。理由のないコメント。構成説明・SPEC・検証記録が、実装と合っているか。件数・行数・版・測定値などの数が、実際と合っているか（出典があるか）。画面の出力例が、実際の出力と合っているか。リンク・見出しのアンカー・改名した型やパスの旧名が残っていないか（`grep -rn` と、リンクの機械的な確認） | 「なぜ」を書いたコメント。当時の記録として残す測定値（日付つき） |
| **テストの質** | 利用者に見える不具合（状態遷移・境界・失敗・許可の判断）を捕まえるか。実装の細部が変わると壊れるテスト。配線・文言の固定。常に真になる検査 | 意図して置いていない低価値の領域 |
| **実行環境の差** | テストが、CI（全ターゲットを 1 つのプロセスで並行に動かす。ローカルとは、並列度が違う）でも通るか。ローカルと CI のツールチェーンの差（版は [開発手順](development.md#ビルドと実行)）で、警告・挙動が変わらないか（CI のログの `warning:`）。Swift 6 モードに上げたときの診断（`-Xswiftc -strict-concurrency=complete`） | 実機・Apple Intelligence・モデルが要るもの（CI にない。[開発手順](development.md#リリース)） |

目印に使える確認（読むための入口で、結論ではない）：

```sh
grep -rn "try?" Sources                  # 握りつぶしの候補
grep -rn "try!" Sources                  # 強制（定数の正規表現・スキーマだけのはず）
grep -rn "@unchecked Sendable" Sources   # ロックで守っているか
grep -rn "TODO\|FIXME" Sources           # 保留
grep -rln "import FoundationModels\|import AppKit" Sources   # 外部依存が入る場所
grep -rn "^import VC" Sources            # ターゲットの依存の実態（Package.swift の dependencies と合っているか）
grep -rn "Process()" Sources             # ProcessRunner に載せていない子プロセス（`ProcessRunner.swift` の 1 か所と、構成説明の負債の 2 か所〔`SaySpeaker`・`DocumentWindow`〕だけのはず）
wc -l Sources/vc/*.swift Sources/vc/Commands/*.swift | sort -rn | head -5   # vc に、判断が溜まっていないか（長いファイルから読む）
```

## このリポジトリの見直し候補

残っている構造上の負債は、[構成説明の負債](architecture.md#既知の構造上の負債)を参照（載せていない `Process`・複製した `Decision/`・Swift 6 モードの診断）。ファイルの分割・設定の失敗の扱い・ターゲットの分割・`vc` の薄型化・`SkillRunner`・`VoiceLoop`・`ProcessRunner`・名前の整理・並行性の監査・テストの置き場所は、済んでいる。PC 操作は、廃止した（2026-11-04）。**2026-11-05 の見直し（MIK-016。v0.1.3 のあとに足したコード）**：スキルを実行するモデルを、アダプター（`ChatModel`）と共通の流れ（`ToolLoopAgent`・`CommandSession`）に分けた（`SkillAgent` と `ToolLoopAgent` は、不変の持ち物だけなので `@unchecked Sendable` を外した）／`vc skills` の `run`（1 つの switch で 150 行）を、サブコマンドごとの関数にし、インストールの流れ（版の決め方・取得・検査）を `RemoteInstall`（`VCSkill`）へ移した（`vc` は、表示と終了コードだけ）／`FileTranscriber` の到達しない `throw` を、平らな 2 回の試行にした／置き場所の違うテストを移した／文言を固定していたテストをやめた。着手するときは、1 つずつ、動作を変えない小さな変更にする。

## やらないこと

- **スコアや件数を、目標にしない**。警告を抑える・テストを通すためだけの変更は、直したことにならない。
- **将来のための抽象・設定・互換の層を、足さない**（YAGNI）。
- **SPEC の要件・数値を、リファクタリングの都合で変えない**。
- **動作確認なしに、成功を宣言しない**。単体テスト・`just eval` の結果と、確認していない範囲を、分けて残す。
- 変更の対象外の、利用者の既存の変更・無関係な整理を、混ぜない。

## 依頼の例

```text
<対象の Module・ファイル> を、docs/refactoring.md の観点で見直してください。
まず、コードを直接読んで、観点ごとに根拠（ファイルと行）を集めてください（ここまで、変更しない）。
次に、観点ごとに判断し、影響が大きく直しやすいものから、小さな変更に分けて提案してください。
私が選んだものだけ、動作を変えずに直し、just test と just eval で確かめてください。
```

## 結果の残し方

PR の説明に、対象・指摘（根拠つき）・実施した変更・確認（テスト・`just eval`）・見送ったものと理由・未確認を書く。構成の理由が変わったときは、[構成説明](architecture.md) を、同じ変更で更新する。
